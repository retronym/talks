What this measures

IncBench replays the same scripted edits on two real builds, scala/scala and scala/scala3, and records how long each incremental compile takes, where that time goes, and what Zinc invalidated to get there.

Three questions share one run:

  • Compiler. Is the integration compiler faster than the commit it is built on?
  • Zinc. Is Zinc's own overhead lower with our fixes on 1.12.x than on plain 1.12.x?
  • Algorithm. Does Merkle invalidation recompile less than name hashing, and does the work it skips outweigh what it costs?

Methodology

The matrix crosses two builds, two compilers and three Zincs: — cells, each running the same — steps.

  • Lockstep. Every cell finishes step k before any cell starts k+1, in a shuffled order each step, so partial results always compare like with like and drift in the machine spreads evenly over cells.
  • In-process Zinc. Each cell is one warm JVM running IncBench from that cell's Zinc checkout, calling Zinc directly with no sbt in between. Every cell compiles the same frozen export of its build; only the compiler and Zinc differ. Before step 1 each JVM is warmed with the clean build and a few small compiles; then a step applies its edit and compiles — time(s). This shows direction and attribution, not precise timings.
  • Two waves. scala/scala's six cells run first, then scala/scala3's, so no more than six warm JVMs are alive at once.
  • Timings. scalac's profiler gives time per phase; Zinc's time is the rest of each compile, split into invalidation, analysis read/write and setup. The API phase includes Zinc's hashing of each class, which runs inside it.
  • Invalidation. Every cycle Zinc runs is recorded: the sources and classes it recompiled and why.
  • Correctness. Each incremental result is compared with a clean build by classfile digest (IncBench --verify), untimed.
