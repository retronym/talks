# IncBench anomalies across builds

The IncBench campaign tooling (`export-build`, `lockstep --verify --profile`, `lockstep-summary`) run on four more Scala 2.13 builds beyond scala/scala, each with the three Zincs in lockstep (1.12.x, + fixes, + fixes + Merkle; integration commits bench f7b7642c03, develop 5615b62e16, merkle 556464169f), all with `recompileOnMacroDef=true` (sbt's default). Results: `~/code/.integration/campaigns/2026-10-20-*-macrodef-true`. See the correction under "The campaign's own defaults". Per-build reports:

- [cats.md](cats.md): typelevel/cats `kernel`, `core`, `free`. Implicits, type classes, kind-projector, specialisation.
- [shapeless.md](shapeless.md): shapeless 2.3 `core` and `examples`. Macro-heavy, with macro users downstream.
- [scala-steward.md](scala-steward.md): scala-steward `core`. Application style, cats-effect/http4s/circe derivation.
- [pekko.md](pekko.md): pekko `actor`, `actor-typed`. Java and Scala mixed, deep hierarchies; run without the scalac optimizer.

Edit scripts are in `../edits/<build>.tsv`, 8-10 edits each (body, public member on a widely inherited type, private member, implicit, sealed case, package object, macro or `@inline`, Java). Raw results are in `~/code/.integration/campaigns/2026-10-20-*-macrodef-true`; the superseded first campaign is in `2026-10-19-*`.

## Findings worth their own investigation

In order of how much I'd want them looked at:

1. **Merkle under-compiles anonymous subclasses declared in a trait's companion** (cats §1). Adding a member to a trait doesn't recompile `object B { new B {} }` when `B` is a trait Merkle decides doesn't read the change, because the local-inheritance edge is a self-dependency that Zinc drops. On cats, 312 stale classfiles in `Order`/`PartialOrder`/`Hash`; a 3-line repro misses a mixin forwarder for an added `def` and a field and accessor for an added `val` (an `AbstractMethodError` at run time). The only correctness bug in Zinc itself found here, and Merkle-only. Being fixed in Merkle's descendant rules (session in progress).
2. **Name hashes of inherited type-lambda members depend on whether the parent was typed from source** (cats §2). Plain Zinc, all versions. An inherited member whose type is a refinement projection naming a class from the parent's own file (`F[One[List, *]]`, or written out by hand) hashes differently when the parent comes from the pickle. In cats, because the members are implicits, every edit that recompiles `OneAnd.scala` ends in a full recompile of `core` (233 sources instead of ~60). kind-projector types are everywhere in typelevel code, so this likely hits every cats-style instance-priority chain. Cause: an eta-expanded alias's type parameter (`List`'s `A`) is owned by the alias's local dummy from source and by nothing from the pickle, so it was named `scala.package.A` vs `A`. Fixed in rz#77/rz#79 with follow-up commits for 2.13 (the first version only fixed 2.12); on cats the full recompiles are gone for those edits. With `recompileOnMacroDef=true` the `OneAnd` flip is still observed (cats §2) and it multiplies the macro cascade of finding 3 into a full `coreJVM` recompile on body edits. Merkle's bridge hasher needs the same rule (in progress).
3. **The macro-dependency rule re-invalidates classes it already recompiled** (shapeless §2, cats §6). `IncrementalCommon`'s third-class invalidation subtracts only the current cycle's classes, so mutually dependent macro-defining sources ping-pong. With the real default (`recompileOnMacroDef=true`) every edit in shapeless costs the whole build, 1,233 classes in 4-5 core cycles (196 source compilations of 83 sources), identically on all three Zincs; on cats, any body edit under `FunctionK`'s dependencies recompiles all of `coreJVM` (1,383 of 1,777 classes, against 2-9 with `false`) because the macro cascade reaches the `OneAnd*` implicits of finding 2. Small, self-contained Zinc fix (subtract every class this run already recompiled for this reason), plus a macro-impl fingerprint (shapeless §1's follow-up) to avoid the cascade altogether.
4. **Merkle's trait-private-member cascade** (cats §3, scala-steward §2). A public addition to a trait changes every subtrait's extraHash, which Merkle reports as `TraitPrivateMembersModified` and handles one inheritance level per cycle. On cats `Functor` it takes Merkle to 1,420 classes against name hashing's 705 (anomaly 2 makes it worse). Fold only the parents' private-member hashes into a trait's extraHash on Merkle.
5. **scalac batch dependence in specialisation** (cats §4). `SortedMapCommutativeMonoid` gets different specialised forwarder return types and is missing bridges depending on what else is in the run. Needs a plain-scalac repro; if confirmed, a scalac bug that can change dispatch.

## The campaign's own defaults

- **Correction: the first campaign ran with `recompileOnMacroDef=false`, which is not sbt's default.** The harness forced it so that scala/scala's fast-track for `macro ???` impls (rz#73) wasn't credited to the other Zincs, but it applied to every corpus. On builds that define macros that made incremental compiles unsound in every cell: shapeless's macro-expansion edit was `missed-error` (examples not recompiled). Rerun with `true` (this README's numbers): the same step is `same-fail` on all three Zincs (incremental and clean fail identically), so there was no Zinc bug. `lockstep` now defaults to `true`; `false` remains a per-cell option (`--cell-option NAME=recompileOnMacroDef=false`) for scala/scala only. Other effects on the earlier results:
  - **Cost.** shapeless: every step recompiles the whole build (1,233 classes) on all three cells, against 145-417 before, and the Merkle advantage on `poly-add-member` (351 vs. 417) vanished. cats: body edits that reach `FunctionK` go from 2-9 classes to 1,383 (cats §6). pekko and scala-steward: no change in counts, as neither module defines macros.
  - **Pekko was run with the scalac optimizer on in the first campaign** (`-opt:l:inline`, set by the pekko build plugin), which Zinc doesn't support. Its anomaly 1 (stale inlined code after editing an `@inline` method) and anomaly 2 (inlining decisions depend on the batch) arose from that and are retracted as findings, not Zinc or Merkle bugs. The rerun is without the optimizer and has no non-`signature` verdict at all.
  - **No new correctness findings** in the rerun: the only non-noise verdict is cats's `bytecode` on Merkle (finding 1, unchanged). New `fresh-mismatch`es on cats `eval-add-case`/`show-*` are scalac batch noise (type-variable names, cats §4/§5) that the first campaign's accidental full recompile used to hide.
  - A sound and cheap alternative (fingerprint the macro impl, invalidate expansion sites only when it changes) is shapeless §1's follow-up.
- **Verify noise from scalac:** quasiquote fresh-name order (shapeless §3; isolated: `Reifiers.nameMap` is a `HashMap` keyed by `Name`, whose hash is its name-table offset; a scalac fix is proposed as its own session), macro fresh-name counters (shapeless §4), type-variable names shifting constant-pool indices (cats §5), (the pekko optimizer inlining noise of the first campaign was retracted, above). None of these is a Zinc problem, but they make `fresh-mismatch` common on these builds. An IncBench improvement would remove most of it: normalise constant-pool indices and local-variable names when comparing.

## Performance

Timings in the rerun come from a loaded machine and are provisional; the comparisons here are on verdicts and recompile counts. Do not read Merkle's higher `analysis` phase as a Merkle cost: the pinned Merkle cells carry a harness bug (IncHandler used an uncached `Locate.definesClass`, fixed in rz#71 4cba55a47, not in the pinned commit) that adds about 100 ms per step to every Merkle cell. The first campaign's "Merkle's analysis costs 2-6x" and the rz#48 composition-cost explanation should be redone once the cells carry the fix.

## Merkle vs. name hashing

With `recompileOnMacroDef=true`, Merkle recompiled fewer classes only on pekko's `ActorRef` (36 vs. 98). On shapeless the macro rule makes every step the whole build in every cell, so the earlier `Poly` difference (351 vs. 417) is gone; on cats every cell recompiles the same on body edits, and Merkle recompiles more on `Functor` (1,420 vs. 709 classes; findings 2 and 4). Outside scala/scala, real builds reach most members through implicits and type-level computation rather than inheritance, so Merkle has less to skip.

## Tooling changes

- `export-build` freezes compiler plugins that the checkout builds itself (shapeless) into `<module>/plugins/`.
- `lockstep-summary OUT_DIR` prints per step and cell the verdict, sources per cycle, wall/scalac/Zinc time with Zinc's largest parts, and each cycle's API changes, and flags verify failures and cells that disagree.
